# Analysis and Measure: guardrails

## How it flows
1. **Analysis (once per answer).** After each capture, `analyseObservationById` runs a pure, rule-based English analyzer with no LLM: discourse → mentions → roles → comparisons → ranks → sentiment → citations → span checks. It links against the run's FROZEN competitive set (`linkableEntitiesForRun`: target + frozen competitors with snapshot aliases and domains + parented products; live confirmed entities only for legacy sets with no pin), sets eligibility (`ELIGIBLE` / `NEEDS_REVIEW` / `NOT_CAPTURED`) and stores one row per (response, `ANALYSIS_VERSION`) in `observation_analyses`.
2. **Measure (on every request, or from a snapshot).** `GET /api/projects/[id]/measure?run=` returns `{measure, run, snapshot, previous, latestApprovedPromptSet, definitions, brandColumns, sourceDefinitions, opportunityDefinitions, comparabilityRules, aggregation, sampling, lowN, readiness}`. `resultForRun` serves the finalised run's `measurement_snapshots` row, else `measureRun`, which:
   - plans from `prompt_runs`, excluding `policy_disabled`;
   - picks one analysis per response, preferring the current version, and reports the versions actually served (`lineage.analysisVersions`, `staleAnalyses`);
   - synthesizes `NOT_CAPTURED` for gaps, with warning `analysis_missing` when a response exists but no analysis row does (coverage: `awaitingAnalysis`);
   - reads the competitive set PINNED to the prompt set (`lineage.competitiveSetSource: pinned | latest_fallback`).
3. **Output.** The pure `computeMeasure` produces `measure.metrics.<combined|chatgpt|gemini>.<key>` plus `presence`, `tradeOffs`, `sentiment`, `sources` (domains + urls + totals), `prompts` (one row per question × engine), `brands`, `opportunities`, `byTopic`, `emerging`, `coverage`, `scopes`, `lineage`.
   - For share of voice and citation share, the numerator and denominator count events or URLs, so the id arrays don't match the counts.
   - `observation_coverage` and `source_capture_coverage` have definitions but no MetricValue; read `measure.coverage`.
4. **History.** `measure/compare.ts` decides comparability (breaks vs cautions) and deltas; `measure/snapshots.ts` writes a snapshot when a run is finalised (`collection/finalise.ts`: automatic when every planned answer is collected and analysed, or `POST /api/collection-runs/[id]/finalise`), lists history (`GET …/measure/history?run=`) and finds the previous run to compare with. `POST /api/collection-runs/[id]/reanalyse` brings a run to the current analysis version and re-snapshots a finalised run. Exports: `GET …/measure/export?run=&format=csv|json`; `GET …/measure/answers?run=` feeds the printable Answers view (`measure/answers.ts`, pure helpers in `answer-evidence.ts` shared with the drawer).
5. **Words from numbers.** `measure/summary.ts` writes the Overview paragraph and the Report summary from the engine's fractions (pure, tested in `tests/unit/measure/summary.test.ts`). Opportunities carry `examples`: verbatim spans quoted as prose, absent in older snapshots. When a metric's meaning changes, the sentences change with it.
6. **Legacy v1 parser.** `src/lib/metrics` still writes `mentions`/`citations` on every capture. Its only reader is `/api/provider-responses/[id]`, and the drawer doesn't render them.

## Invariants
- **Gaps are never absences.** `NOT_CAPTURED` and `NEEDS_REVIEW` leave **both** the numerator and the denominator. They appear only in coverage and scope exclusions.
- **Zero denominator → `null`.** The UI shows `—` or "No answers to count yet", never 0%.
- **Sections never blend.**
  - Presence metrics (visibility, brand-free rate, share of voice, first choice, presence rows, topics) use **Discovery** only.
  - Trade Offs count verdicts only.
  - Sentiment Analysis (labelled "Reputation" in the UI) counts target portrayal only.
  - Citation metrics use all sections.
  - Known exception: the emerging "Also named, but not tracked" list is built from every section.
- **Presence** is binary per (observation, entity). It counts only `exact`/`strong` occurrences (`AGGREGATABLE_CONFIDENCE`).
- **Competitive denominators** contain only the target plus the frozen competitors. Emerging brands never enter one.
- **Ranks** exist only on rank-eligible answers.
- **No opinion → `NO_SENTIMENT`**, never positive.
- **Cited is not present.** Appearing as a source doesn't count as being named.
- **Undecided is not a loss.** `TIE`, `UNCLEAR` and `NEITHER` never count as losses; win rate uses decisive answers only.
- **Exact spans.** Every Span must slice back to its exact text; a mismatch sets `NEEDS_REVIEW`. Analyses are additive, and `provider_responses` is immutable.
- **Definitions travel with the numbers.** The "?" drawer renders `METRIC_DEFINITIONS` verbatim. The measure page still restates some rules in hint copy: once per answer, verdict-only Trade Offs, no-opinion ≠ positive, emerging brands excluded from SoV, gaps left out, `LOW_N`. When a definition changes, update that copy too, and don't add new restatements.
- **Pure core, thin shell.** `analyzer.ts` and `engine.ts` do no I/O. Services and routes do the DB work.
- **No brand lists.** The link inventory comes only from project entities:
  - the target, confirmed entities, and parented product/sub-brand entities (any status);
  - surfaces: canonical names, aliases, derived short names (a capital letter required) and simple plurals.
- **Fixture discipline.**
  - Gold and holdout cases are author-constructed; never tune against holdout.
  - When the analyzer disagrees with a label, assume the code is wrong.
  - Change a label only when the label itself is wrong, and annotate it `LABEL CORRECTED` with the reason.

## Version rules
- **Bump `ANALYSIS_VERSION`** (`analysis/types.ts`) whenever output for the same input changes. That includes:
  - any `analysis/*.ts` rule;
  - the `NormalizedObservation` shape;
  - the entity inventory or input mapping in `analysis/service.ts` (`linkableEntitiesForRun`);
  - `landscape/name-forms.ts`;
  - the capture-state → eligibility mapping;
  - a `tldts` upgrade.
- **Without a bump,** analyses never change: `analyseObservationById` returns the stored (response, version) row.
- **After a bump,** Measure keeps serving the stored rows and says so: `lineage.analysisVersion` becomes the older version (or `mixed`), `staleAnalyses` counts the rows behind, and the page's "Update results" banner offers re-analysis (`reanalyseCollectionRun`, additive, no v1 duplicates). Finalised runs get a new snapshot superseding the old one. `scripts/reanalyse.ts` still exists and still duplicates v1 rows; prefer the endpoint.
- **Bump `METRIC_POLICY_VERSION`** (`measure/policy.ts`) with any change to a numerator, denominator, unit, section filter, aggregation rule, brand/source/opportunity definition or comparability rule, and edit the definitions in the same change. A finalised run keeps serving its snapshot at the old policy version until re-finalised; live runs re-render immediately. Two runs at different policy versions are a comparability break.
- **`AGGREGATABLE_CONFIDENCE` is read live by `measure/engine.ts`.** Bump both versions.
- **Snapshots are additive.** `measurement_snapshots` has one row per (run, analysis versions, policy version); re-finalising at the same versions refreshes the row, at new versions inserts a superseding row. Never edit a stored `result`.

## Pitfalls
- **Frozen vs live sets.** Measure and analysis both use the prompt set's pinned competitive set. A rival confirmed later is untracked (`emerging`) in earlier runs until a new prompt set is approved and a new run collected; that run is then a comparability break.
- **Exact section literals.** Sections must match exactly (`'Discovery' | 'Trade Offs' | 'Sentiment Analysis'`). A null or renamed section silently drops the observation from every section metric.
- **Analysis failures are visible now.** A response with no analysis row shows as "awaiting analysis" in coverage, the console and the Performance table, with a re-analyse action; the run stays open (never auto-finalised) until it is analysed.
- **Two definitions of "captured", reconciled.** `coverage.captured` counts collected answers (including ones awaiting analysis); `analysable` counts ELIGIBLE analyses. The console shows both.
- **Hedged recommendations.** Hedge terms in the clause (`HEDGE_TERMS` in `analysis/discourse.ts`: may, might, could, often, generally…) make a RECOMMENDED role weak, and occurrence confidence is the weaker of link and role (`analyzer.ts`). So "could be a good option" drops the brand from presence while the answer stays in `discovery_visibility`'s denominator.
- **Don't use `force` on real data.** `analyseObservationById(…, {force:true})` overwrites the current-version row in place, which breaks the "analyses are additive" rule. Nothing calls it today.
- **Scopes are engines, not routes.** A route missing from `ROUTE_ENGINE` (`providers/engines.ts`) is mapped by name. Add new routes explicitly.
- **The measure page** masks a non-404 API error as the empty state; a foreign run id gets its own "isn't here" message.
- **Untracked names are businesses of the measured kind (`observation-analysis@12`).** `detectEmergingCandidates` takes an `EmergingContext` (`service.ts` `emergingContextForRun`, cached a minute per run: places and category words from the run's frozen prompt context plus the profile's branches and nearby areas; product forms learned across the run's answers with `learnProductForms`; the analyzer adds the tracked entities' names) and keeps a capitalised run only when it is a business of the measured kind: named with a category word ("MH3 Gym", "GymNation"), listed as an option (a bullet or bold label followed by a dash, the first cell of an option table — decided from the header row, never an attribute table like "| Feature | Zoho CRM | Pipedrive |" — an own-site link opening a row, or a map listing with the rating on the next line), or in a sentence that names the kind. One word alone also needs a cue: a brand shape (camel case, digits, five or more capitals), a list entry, an introduction ("brands like Hoka", "vs Saucony"), a capitalised list neighbour, a business verb ("Rajdhani serves"), or a second mention. Dropped: places (the project's own, well-known countries and cities, area or landmark shapes, "Al"/"Umm"/"Wadi" prefixes, Indian and English toponym endings, area codes such as JVC unless a brand cue is present, a name before "Mall"/"branch", after "in"/"on"/"near"/"across" or "cities like", or beside places in a comma or slash list — a place anywhere in an answer is a place everywhere in it); products of tracked brands ("Nike Pegasus 40" anywhere in the run makes "Pegasus" a product), model numbers ("Air Force 1", "Nano X3"), things followed by "foam"/"fabric"/"line"/"shoes", features ("the Quick Help menu", "Lead Source field"), modules named for a function ("Leads Inbox", "Marketing Cloud"), ingredients, people (titles, athletes, endorsements), shopping and lead-source channels ("from Zappos" in a buying sentence, "leads from Facebook"), sports teams, technologies ("supports Java, Python"), integration pairs ("Pipedrive + Slack"), flow steps ("New lead → Contacted → Won/Lost"), quoted terms (“ABC Inc.”), jargon (B2B, SaaS), compound qualifiers ("CRM-linked"); examples the answer asks about ("If you tell me what tools you connect (e.g., Gmail, Outlook…)", a list under such a colon) and open "etc." or "e.g." lists; phrases made only of category, cuisine, dish, compass, module and modifier words ("South Indian", "Running Apparel", "Chicken Biryani", "Mutton Rogan Josh"); sentence fragments, field labels, attribute and activity words ("Durability", "Tennis"), colours, weekdays, months, currencies, holidays and sale days, plural acronyms, file names and URL fragments, the description after a dash ("— Convenient"), a word listed among lower-case things ("boxing, HYROX and…"), a one-word label heading two or more other names, and names that only ever appear as trailing citation labels (`[AE Profile](ae-profile.com)`, `[CRM Compared](crmcompared.com)`). A trailing place or possessive is cut ("SK Fitness Dubai" → "SK Fitness", "Saucony’s" → "Saucony"), a product with generic words keeps its maker ("Gymshark Performance T-Shirt" → "Gymshark", "HubSpot Sales Hub" → "HubSpot"), a short form folds into the longer name only when the longer adds a business-type word and is not the rarer form ("MH3" → "MH3 Gym"; "GymNation Downtown", "Hoka Clifton" and "Salesforce Sales Cloud" fold to the brand), what an answer writes after a kept name is that name's product, and a tracked business's own forms ("Warehouse CrossFit" beside "The Warehouse Gym") are never proposed. Runs never cross a line break (a map listing's "Open" line no longer glues onto the name below). Without a context (legacy callers, tests) the older mid-sentence rule stands. The analyzer then keeps a candidate when its strongest role across every mention is RECOMMENDED, COMPARED or DISCOURAGED, or when the detector saw it as a listed option; judging the first mention alone had dropped HubSpot from a CRM answer while keeping three integrations. Cross-project probe 2026-09-16: a Dubai gym's list is 32 fitness businesses, Bengaluru and Dubai restaurants list restaurants and venues, a CRM (Pipedrive) lists 21 software tools with no channels or jargon, and a global shoe brand lists rival apparel, retailers and untracked rivals' product lines as the remaining leak.
- **Option labels are read whole (`observation-analysis@15`).** With a context, `detectEmergingCandidates` first judges every option label (`optionLabels`: a bold label before a dash, a bold "Name — Area" pair, a plain label before an em/en dash, a map entry with its rating line above or below) through `cleanOptionName`, which cuts at `|`, a dash, a bracket or a comma, drops Arabic/Hebrew script, legal tails and dangling "by/of/&", a trailing place, and a branch's area after the last business word ("N.Bar Nail Spa & Salon Emirates Towers" and "… Gate Avenue" are one salon). A name a label proves is kept whole wherever the answer repeats it (five-word names and names with "&" survive; the short head "House" no longer wins the fold over "House of Burn"), and the text after an option's dash is a descriptor zone: an area there ("— Azizi Riviera.", "— Carlton Downtown Hotel.") is never a business unless an introducer ("or try X") precedes it. Names with "/" ("Attribution/reporting") are headings, not businesses. A DIFC salon's "who ChatGPT names" list was led by a residential tower and a hotel before this.
- **Verdicts, conditions and the asker (`@13`–`@16`).** Trade Off verdicts read "I'd lean toward X" (only when the question names the rival), and a verdict written after the chosen name ("X has the stronger documented case", "has the edge", `CHOSEN_BEFORE` in `comparison.ts`); when each side is chosen under its own condition ("Choose A if …; choose B if …"), there is no verdict. "Depending on where you are" is a condition, and "there isn't enough evidence to say X lasts longer than Y" is not a comparative. Sentiment ignores the asker's own problem or condition ("if your main issues are frizz …", "if your nails are weak") and an offer to search ("I can dig through reviews for complaints"), but "If your hair is damaged, X is a poor choice" stays negative. Coded names link by their head ("Y12" for "Y12 Salon", link-only, never a prompt name). Reading every answer of one salon's run found all three recorded head-to-head losses and every negative reading were misreads.
- **A tracked business links by its head word once an answer names it in full.** `linkProvenHeadForms` (after `detectMentions`) links "Warehouse" to "The Warehouse Gym" and "Gold's" to "Gold's Gym" only inside an answer that already linked the full name, when the head has five or more letters, the dropped words are business-type words, the head is not a category term and the answer never writes it in lower case. It is never a stored alias. `detectMentions` also matches straight and curly apostrophes interchangeably. Seventeen "Warehouse" mentions of a Dubai gym were counted as an untracked brand before this.
- **Tracked-only share of voice is export-only since measure-policy@4.** Earlier: **Share of voice was shown as "Not comparable" when no tracked competitor was named.** Its denominator is the target plus the frozen competitors only, so with no competitor named the share is 100% by construction ("3 of 3" for a gym whose answers named Fitness First and GymNation, both untracked). `shareOfVoiceReading` (`summary.ts`) decides; the Overview card, the Report figure, the Brands share bar and the "In short" sentence all say what happened and name the untracked brands instead. The definition's reproducibility rule (untracked names never enter the denominator) is unchanged; the fix for the project is to confirm the rivals the answers name and collect again.
- **Share of every business named is the headline share (`measure-policy@3`), labelled "Share of voice" since @4.** At @4 untracked names are one business however spelled (`businessKey` in `engine.ts`: case, apostrophes, "&"/"and"), so "ALKEMY Salons" and "Alkemy Salons" no longer split. Share of voice counts only the tracked rivals, so a DIFC salon read 88% while ChatGPT named 27 businesses in the same answers and the salon took about 15% of those mentions. `discovery_share_all_names` counts one presence event per (answer, business) for the target, the frozen rivals and every untracked business the analysis detected, so it inherits the untracked detector's quality and is specific to one run (not a reproducible competitive set). The UI calls `discovery_visibility` "Named unprompted" and shows the new share beside it; share of voice stays, labelled as tracked-only. `measure.byPlace` breaks Discovery presence down by the place each question named (`service.ts` `placeOfQuestion` matches acronyms such as DIFC to their long form), with the most-named other business per place. "Missing from discovery" opportunities count answers that named other businesses, tracked or not. Examples quoted on opportunities need two words and are never a map rating line ("4.9•Hair salon").
- **Findings live on the Overview (`measure-policy@4`).** The Opportunities tab was retired: `?view=opportunities` opens the Overview at `#findings` (`components/features/measure/findings.tsx`). Missing-from-discovery and head-to-head losses are ONE finding each (items: businesses named instead; rivals with their aspects); `rival_source` and `owned_uncited` are no longer produced (they restated Sources figures) but keep definitions so old snapshots render. A quote must say something beyond the names in it (`saysMore` in `exampleSpans`).
- **"No business named" (`answer_brand_free_rate`) counts answers naming no business at all, tracked or untracked (@4).** It counted answers naming no TRACKED brand, so a list of six untracked salons was "brand-free".
- **Every headline rate carries a plausible range** (`measure/precision.ts`, Wilson 95%) once it has `LOW_N` answers, and a run-to-run change inside the earlier run's range is marked `withinRange` and shown neutral, never as a gain or a loss. The sampling posture is "Exploratory baseline" (IAB, August 2026: under 50 queries is exploratory).
- **Option lists in the October 2026 ChatGPT layout (`observation-analysis@18`).** Numbered names and headings with a listing below ("1. Maria Dowling" over "Al Mina · Colour specialist", "## 1. ELAN Lash & Brow Beauty Lounge" over "4.9/5 · 1,272 reviews") are option labels (`numberedName` in `mentions.ts`, gated by `LISTING_CUE` so advice lists stay out); a tracked name inside any option label is RECOMMENDED; rank eligibility counts untracked options too, and an untracked option on a numbered line holds its number (prose order stays tracked-only). A salon's "best lash extension salons" answer listing six ranked salons read as naming no business before this.
- **Absence of a complaint is not a complaint (@18).** `sentiment.ts` masks "I couldn't find a … complaint", "no complaints were found", "the lack of complaints" and a restated search ("to see whether anyone has reported …"); "if you like …" is an offer only when an offer follows ("If you'd like, I can …"). Across 130 by-name answers this removed 7 false negatives and restored 2 dropped positives.
- **Opportunities are evidence, not advice.** Each type's definition states what it is and is not evidence of; source gaps are answer-level facts until a persisted page fetch exists. Do not add benchmarks, volumes or revenue.
